# LoRA研究台帳：初版仕様

作成日：2026-09-12
状態：初版を実装。操作方法と検証結果は [使い方](lora-research-ledger-usage-ja.md) を参照。画像の人間評価は未入力。
基準コード：`92a6f6228f4d660a9900fefb36c679c1ea7f89dd`。既存のログ形式と設定記録の仕組みに合わせた台帳の仕様を記す。

追記：旧checkpointのメタ情報からの設定取得、学習後のファイル改名、任意の5項目（お気に入り度・学習の目的・良いところ・悪いところ・任意メモ）を反映。入力は全欄任意とし、比較を必須にしない。

GUIはユーザー指定のPySide6とする。ツールはsd-scripts内、台帳・参照先設定はリポジトリ外。普段の登録は複数の参照先を再走査する入口にまとめ、閲覧・編集はGUI、CSVは書き出しとする。

## 1. 決定すること

**元ログ・重み・画像は現在の保存場所に置き、学習と成果物の識別情報、比較条件、人間の判断だけを小さなJSONへ保存する。**

初版の機能は「登録」「評価」「分析用出力」の3つ。必要なときに起動する日本語のPySide6デスクトップGUIを用意する。人が編集する正本はJSON、集計は再生成可能な派生物とする。外部サービス、常駐監視、学習ループ内の追加計測は初版に必要ない。

最初の完成価値は、過去の判断を正しい重みと条件に戻せること。画質を予測する法則の発見を、台帳の完成条件にはしない。

| 論点 | 初版の決定 |
|---|---|
| 登録単位 | 実行ごとのrun。epoch・最終版・final_raw等はその下の個別成果物 |
| 評価単位 | 特定の成果物と生成条件を使い、特定の画像集合を見た判断 |
| 人間評価 | 相対的な好み、用途内の実用性、実際の採用を分ける |
| 必須入力 | 評価値・文章の必須欄なし。登録だけ、目的だけ、星だけでも保存可能。対象は選択中のrun・重みを自動設定 |
| 通常の任意入力 | お気に入り度★1〜5、学習の目的、良いところ、悪いところ、任意メモ |
| 詳細の任意入力 | 比較の第一候補、実用性、採用、本人らしさ、顔・人体の自然さ、各欄の理由 |
| 旧学習の設定 | 対応済み設定ファイルがなければ、対象checkpoint自身のメタ情報から記録済み項目を取得 |
| 名前 | 修正後の現在のファイル名を一覧・検索の基本にし、内部のoutput nameを別名として保持 |
| 既存ログ | 読み取り専用。曖昧な対応でも仮登録できる |
| 集計の入口 | 既存診断JSONと既存研究の小さな集計を再利用。必要な項目だけ元ログから抽出 |
| 重みの処理 | 登録時は一覧とヘッダー中心。選んだ重みの同一性確認、追加解析を分ける |
| 画面 | PySide6の主画面に一覧と詳細・評価を並べる。参照先設定と再走査結果は別ダイアログ |
| 参照先 | 複数フォルダを登録。lora_output配下の既知サブフォルダを自動検出 |
| 通常の追加 | 再走査 → 差分確認 → 新規登録・追加資料の反映。登録済みは重複させない |
| 配置 | ツールはsd-scripts内。台帳と参照先設定はリポジトリ外。GUIの起動状態だけリポジトリ内のGit除外ファイル |
| 閲覧・編集 | GUIを正本の操作画面とし、Excel向けCSVは閲覧・集計用に書き出す |
| 初回運用 | 過去の5〜10比較で登録と評価を試し、以後は普段の比較時に追加 |

## 2. 対応する入力と設計方針

### 2.1 対応する入力と再利用先

学習出力フォルダとその配下の `diagnostic_report`、`run_records` などを探索する。ファイル数にはコピーや同一runの複数成果物も含まれるため、独立した学習回数として扱わない。

| 種類 | 用途 |
|---|---|
| 診断JSON（`diagnostic_report/*_diagnostic.json`） | 記録済みの診断指標 |
| 学習設定manifest（`run_records/**/manifest.json`） | 学習設定と実行の対応確認 |
| gradientログ | 勾配指標の推移 |
| DQ・DQ autoログ | 量子化指標と自動調整の記録 |
| rankログ | rank関連指標の推移 |
| group lossログ・epoch集計 | グループ別loss |
| avg shadow/promote JSONL | 平均化と採用イベント |
| safetensors | メタ情報とcheckpointの識別 |

再利用するコードと任意入力：

- `library/training_settings.py`、`tools/lora_training_settings.py`：UUID、session・開始時刻との照合、設定の出典と欠測処理。`settings_status=resolved` は完走の証明ではない。
- `tools/make_lora_diagnostic_report.py`：loss、DQ、rank等の診断JSONとHTML。
- `sdxl_lora_report_cui.py`：`metadata.json` に条件・prompt・seed・job・画像パス、`config.json` に生成設定を保存する。TE1/TE2/UNet別強度とLBWも扱う。
- 任意の既存研究集計：索引やepoch集計を出典付きで参照する。大きなデータベースは台帳へ複製しない。
- 任意の過去の人間評価：対象の重み・生成条件・評価軸を確認して登録する。既存報告の主張を独立に再検証したものとして扱わない。

### 2.2 設計上の判断

1. **新しい巨大な集計基盤は作らない。** 既存研究の索引・集計を出典付きで接続する。ただしファイル名による対応候補を、確定runへそのまま昇格させない。
2. **現行のブラインド票は自動で取り込めるとは限らない。** 現行コードの `reveal()` は画面上の選択から得票を表示するが、投票を書き出す処理はない。`metadata.json` に人の投票結果は入っていない。
3. **診断JSONだけを完全な原本としない。** 現行のDQ変換では元ログの `Scope`、`Target`、`RMS` 等が省かれる。平均化JSONLも独立している。統計用の定義確認には元ログまたは定義と出典を保持した既存集計が必要。
4. **重み全件のハッシュ計算・解析を初回登録に含めない。** 大量の重みファイルの全読込を開始操作の条件にすると、台帳の軽さを損なう。
5. **訂正と再評価、同点と未評価をデータ上で区別する。** 名前や最新の画面表示だけでは過去の判断の意味を保てない。

## 3. 日常の使い方

### 3.1 過去の学習を登録する

1. 初回起動で、外部の台帳フォルダを新規作成または既存台帳として開く。
2. 「参照先設定」で学習出力の親フォルダを登録する。標準の子フォルダは自動で見つける。別の保存先も追加できる。
3. 「再走査」で登録候補・差分を表示する。検索範囲は有効な参照先内。重みのテンソルは読まない。
4. 「新規登録・資料追加を反映」で対応を確認できたものをまとめて反映する。不明な候補は個別に確認するか仮登録できる。
5. まず覚えている5〜10比較に評価を付ける。全runの採点を要求しない。

重みが消えていてログだけ残るrun、評価の記憶しか残らないrunも登録可能。利用できる分析の範囲が違うことを表示する。

### 3.2 新しい学習の後に登録する

学習・既存レポート生成の完了後にGUIの「再走査」を押す。既存登録との違いを確認して、新規学習・追加のcheckpoint・後から生成したレポートを反映する。初版はこの操作で完結する。CLIも同じ処理を利用し、後からbat末尾へ追加できるようにする。

無人登録は、明確に対応できるものを登録し、曖昧なものを仮登録する。プロンプトで夜間処理を止めない。登録失敗はログへ残し、学習の成否を変更しない。

既存の設定記録だけはUUIDで分離されるが、通常のログ名・重み名はそれだけでは保護されない。新しい学習では実行ごとに出力フォルダか出力名を一意にする運用を採用する。初版の台帳が既存ファイルを移動・改名することはない。

### 3.3 普段の比較で評価を残す

1. 詳細画面から画像比較レポートを開く、または比較レポートのフォルダを指定する。
2. 候補、重み、生成条件、閲覧する画像範囲を取り込む。
3. いつもの比較を行い、総合の第一候補等を選ぶ。
4. 余裕があれば実用性、本人らしさ、自然さ、理由を足して保存する。

比較せず記録する場合は、対象run・重みの「メモ・お気に入り」から通常の5項目だけ保存できる。目的の記録も、星だけの記録も可能。上の比較手順は必要な場合だけ行う。

「登録済み・評価済み」をrun全体の品質として表示しない。一覧には「final、強度0.8について評価済み」のように対象を併記する。

### 3.4 ログ等の参照先を設定する

「参照先設定」はフォルダの一覧表にする。列は有効／名前／フォルダ／サブフォルダも探索／認識した資料種類。操作は「追加」「場所を変更」「外す」「検出内容を見る」。フォルダ選択ダイアログを使い、パスを毎回手入力させない。

以下は架空の配置例。学習出力の親フォルダを1行登録すれば、配下の既知のログフォルダも探索する。実際の保存場所に合わせて設定する。

```text
参照先：学習出力
D:\lora-workspace\lora_output
サブフォルダも探索：ON

  直下のログ・checkpoint          → 学習と成果物
  run_records/                   → 学習設定
  diagnostic_report/             → 学習の診断レポート
  dq_dataset_profiler/            → データセット診断の関連資料
```

4フォルダを別々に登録する必要はない。保存先が分かれている場合は、別の参照先を追加する。例：`D:\lora-workspace\lora_reports` を「画像比較」として登録。既存研究フォルダや移動済みのログ置場も同じ一覧で管理できる。固定のDドライブ・親子構成に依存しない。

探索は既知形式の候補を列挙し、中身のkind/schema・構造を確かめて分類する。画像・重みテンソルの全読込はしない。通常はjunction・symlinkを自動で辿らず、対象にしたい保存先は明示的に追加する。除外フォルダは詳細設定で指定でき、台帳自身、キャッシュ、venv、.git等を走査しない。

親と子を重ねて登録しても、正規化した実パスで同一ファイルの探索を重複させない。どの参照先から見つけたかは保持する。コピーが別パスにある場合は既存のID・内容hashによる重複規則を使い、statだけで内容一致とはしない。

`dq_dataset_profiler` は通常の学習とは役割が異なる。診断の中間ファイルやsnapshotを新しい通常学習として登録しない。レポート・設定の参照を「関連資料」として見つけ、dataset/runへの対応が確認できたときに結び付ける。対応がない資料は再走査結果の「関連資料のみ」に残し、通常学習一覧を増やさない。未接続資料の検出一覧は再生成できるキャッシュ、接続済みの参照はrunカードの正本に保存する。

参照先を外す操作は今後の探索から外すだけ。台帳の登録・評価や元ファイルを削除しない。登録済み参照が使っているroot対応表は保持する。ドライブ移動では新しい参照先の追加より「場所を変更」を使い、同じroot IDを保つ。

### 3.5 再走査と差分の反映

再走査結果はファイル数と学習候補数を分け、次の状態で表示する。1回の学習でepoch重みが40本増えても、新規学習40件とは表示しない。

| 状態 | 例 | 既定の処理 |
|---|---|---|
| 新しい学習 | 未登録のrun、旧checkpointから新たに識別した実行 | 新規登録候補にする |
| 登録済み・追加資料あり | 同じrunに新epoch・final_raw・診断JSON・比較レポートを発見 | 既存runへ追加する候補にする |
| 登録済み・変更なし | 同じ識別情報で通常の差分検査に変化なし | 何も増やさない。通常は折りたたむ |
| 変更あり・要確認 | 同じパスの内容変更、設定矛盾、対応が曖昧な改名 | 旧評価を保ったまま個別確認 |
| 見つからない | 前回の参照を今回見つけられない | 登録を残して状態表示。削除しない |
| 出力中・読込不能 | 走査中に変化、途中書込、権限不足 | 確定せず次回再走査または再試行 |
| 関連資料のみ | 対応する学習が未確定のdataset診断・画像レポート | 通常学習へ自動昇格させず、関連付け候補として表示 |

同じパスの診断JSONが再生成された場合は「追加」ではなく「変更」。旧出典を残し、新しい版として取り込む候補を表示する。重みの置換は別artifactとして扱う。出力名が同じでもsessionが違えば別run候補。名前しか根拠がなければ自動統合しない。

画面上部に「新規N件／追加M件／要確認K件」を出し、正常な新規・追加を既定選択にする。「新規登録・資料追加を反映」でまとめて保存する。要確認を自動承認したことにはせず、仮登録・関連付けの確認を個別に行う。毎回すべての登録済みファイルを確認させない。

初回走査後はファイル一覧とstat・既存ID・読取結果を小さなキャッシュへ保存し、通常の再走査では変更のない大きなJSONを読み直さない。形式や取込器の版が変われば対応するキャッシュを無効化する。通常の差分検査と完全hash検証は区別する。

走査と反映を分ける。反映直前に対象ファイルの状態と台帳の改訂番号を再確認し、走査後に変わった対象は保留にする。1件の問題で他の正常な新規候補まで止めない。中断・再実行で登録を二重にしない。

参照フォルダ全体が接続不能の場合は「参照先にアクセスできない」と表示する。配下全件を削除済みと判断しない。学習中かどうかを短時間のstat不変だけで確定せず、完走状態の既存規則を守る。

### 3.6 台帳への登録経路

**通常のファイル付き学習結果の入口は、参照先の再走査に一本化する。参照先フォルダは複数持てる。** 初回も次回も同じ操作で、新しいrunと既存runへの追加資料を扱う。

例外は元ファイルが残っていない過去実験の「メモだけ登録」と、見つかった関連資料・外部メモへの手動の関連付け。これらも同じ台帳処理とID・履歴規則を通す。別の台帳やCSV編集による登録経路は作らない。

CLIはGUIと同じ走査・反映処理の呼出し口。初版でCLI操作を普段の必須手順にしない。個別ファイルのドラッグ＆ドロップ等は必要になってから同じ候補確認へ接続し、初版の完成条件にはしない。

## 4. 人間評価の定義

### 4.1 3つの判断を分ける

| 判断 | 値 | 意味 |
|---|---|---|
| 相対的な好み | 第一候補／同程度／判断保留／未評価 | 見た候補と画像集合の中での比較 |
| 単独での実用性 | 使える／条件付きで使える／この用途では使いにくい／未判断 | 他候補がなくても、この用途で使うか |
| 実際の採用 | 候補を1つ以上選択／今回は採用なし／未決定 | 実際の運用判断。品質ラベルへ変換しない |

用途は日本語の短い名前でよい。初期値を「普段のキャラクター生成」とし、変更内容を評価ごとに保存する。全用途共通の絶対合否とは呼ばない。

相対評価の軸は `overall`（総合）、`identity`（本人らしさ）、`naturalness`（顔・人体の自然さ）の3つ。「比較を記録」を開いた場合は総合を先に表示し、残り2つは任意入力。各軸に理由欄、各候補の実用性にも理由欄を持つ。「総合メモ」だけに集約しない。

主観的な「お気に入り度」は5段階で入力できる（4.5）。軸を勝手に足し合わせた品質スコア、全用途共通の品質ランキングは作らない。

### 4.2 第一候補から作ってよい関係

「A・B・Cを見てBが第一候補」で保存した場合：

- B > A、B > Cを記録できる。
- AとCの優劣は不明。
- B以外も「使える」でよい。
- 3候補すべて「使いにくい」でも、Bを第一候補にできる。

比較の対象リストとは別に、**その軸で実際に比較した候補リスト**を持つ。Cが生成失敗・未閲覧ならB > Cを作らない。

「AとBは同程度」を明示した場合だけ同点とする。「AとBのどちらも候補にしたいが決められない」は判断保留。複数の第一候補を選ぶ操作では「同程度と判断した」か「決められない」かを選べるようにする。

内部の相対関係は候補対ごとに `left / right / tie / undecided` と、軸・理由を持つ。未評価は関係を作らない。第一候補の操作から生成された関係には、その事実と同じ判断イベントIDを付ける。1回の3候補選択を2回の独立実験として数えない。

人による生成画像の選好を対比較として保存する先行例は [Pick-a-Pic](https://arxiv.org/abs/2305.01569) にある。記録方法を参考にするもので、この規模の個人実験で同等の予測性能が得られるとする根拠ではない。

### 4.3 保存例（架空）

用途：普段のキャラクター生成。A・B・Cの指定画像集合を今回見直した。

| 候補 | 総合 | 単独での実用性 | 実用性の理由 |
|---|---|---|---|
| A：run A、epoch30、強度0.8 | Bより好みでない | 使える | 十分似ているがBの表情が好み |
| B：run B、final、強度0.8 | 第一候補 | 使える | 狙った顔立ちで安定している |
| C：run C、final_raw、強度1.0 | Bより好みでない | 条件付きで使える | 正面はよいが横顔を選ぶ |

本人らしさはB、自然さはAという別の判断を記録できる。採用はB。AとCの順位は未記録。強度が異なるので、これは実際に使いたい生成条件の比較であり、学習設定だけの効果を検証した比較ではない。

### 4.4 評価の背景と履歴

比較・画像に結び付いた評価には以下を保存する。自動で分かる内容は入力させない。短いメモ・お気に入りの段階で分からない生成条件や閲覧範囲は、不明のまま保存できる。

- 評価者、評価日時、用途、評価基準の版。複数キャラの学習では、評価したキャラ・groupも保存する。一部キャラの本人らしさを、全キャラの評価へ広げない。
- `evidence_mode`：今の再評価／当時の保存評価の取込／記憶からの登録。記憶は当時の日時を推測して埋めない。
- `selection_mode`：指定した全ケース／選別した一部／不明。選別した良画像はその用途の記録として残し、全体の成功率には使わない。
- `blinding`：名前を伏せて評価／名前を見て評価／不明。今回見直したこととブラインドかどうかは別項目。
- 見たレポート、候補、ケースIDまたはprompt・seedの組、見た範囲。単なる「全体」は、その時点の具体的なケース集合として固定する。
- 比較の狙いと意図した差（任意）。例：DQだけ変更、checkpointだけ変更、普段使う強度へそれぞれ調整。

誤入力の**訂正**は同じreview IDの新しい版として保存する。判断をやり直した**再評価**は別review IDにし、前の評価へ `reassessment_of` でつなぐ。どちらも以前の版は残す。採用だけ変更した場合も、変わった欄が分かる版を残す。

集計は各reviewの最新版を使う。同じ対象の再評価を独立した反復として加算せず、標準では同じ評価者・用途・基準・候補・ケース集合につき最新の再評価を採用する。過去の変化を調べる場合だけ履歴を別集計し、採用したreview IDを分析記録に残す。

### 4.5 普段使う5項目：全欄任意

5項目を通常入力として採用する。画面に並べる欄の数より、毎回すべて埋める運用にしないことを重視する。空欄のままでも登録・保存でき、必須採点・入力完了率・未入力警告は設けない。

| 表示名 | 保存先・形式 | 意味・使い方 |
|---|---|---|
| お気に入り度 | 対象ごとの `favorite_rating`。整数1〜5またはnull | 自分がどれくらい気に入っているか。客観的な品質点・採否・実用性とは別 |
| 学習の目的 | runの `user.experiment_note`。複数行文字列 | 「clip_rate_highを試す」「昨日の機能実験。その機能は正式採用しなかった」等。目的とその後の経緯を同じ欄へ書ける |
| 良いところ | reviewの対象ごとの `good_points`。複数行文字列 | 「破綻が少ない」等 |
| 悪いところ | reviewの対象ごとの `bad_points`。複数行文字列 | 「キャラの再現性が低い」等 |
| 任意メモ | reviewの対象ごとの `free_note`。複数行文字列 | 比較、目の違和感、崩壊気味等を自由に記録 |

星の初期ガイドは、★1「あまり好みではない」、★2「やや物足りない」、★3「まずまず好き」、★4「かなり好き」、★5「特にお気に入り」。厳密な採点基準は要求しない。未評価は星なしで、0点ではない。「評価を消す」でnullへ戻せる。前の入力は履歴に残す。

お気に入り順の一覧・絞込みは用意する。★4でも比較では負けてよく、★2でも実験の目的を果たしてよい。同じ星の2候補を同点扱いせず、星の大小から対比較の票を作らない。数値の間隔が等しいと仮定した万能スコアを作らず、初期の分析は件数・分布・同条件内の順位を使う。星を研究へ利用した場合は主観的な値であること、対象・評価時期・未評価数を示す。

「学習の目的」は生成画像の用途や通常学習／試験／診断の分類とは別欄。「その機能は正式採用しなかった」は実験した機能の採否であり、LoRAの不採用・画質不良へ自動変換しない。

良いところ・悪いところ・任意メモは固定タグへの変換を要求せず、原文を保持する。悪いところの空欄は「欠点なし」ではない。AIが後から分類・比較相手を抽出する場合は出典付きの派生情報とし、原文を変えない。「Bより良い」という文章だけからBのIDを断定したり、確定済みの比較票を追加したりしない。任意の「比較相手を選ぶ」で正しい相手に結び付けられる。

目的だけならrunカードの更新、星や所見があればreviewカードの作成・更新とする。全欄空のまま保存しても、空の評価イベントを増やさない。

具体的な重みを選んでいればそのartifact・分かる生成条件に評価を付ける。学習名だけに付けた思い出・所見は `target_scope=run_impression` とし、checkpointは不明のまま保存する。画面では「学習全体の印象」と表示し、全epochへ展開せず、checkpoint単位の品質分析からは除外する。後から対象を確認できた場合は履歴を残して結び付ける。複数キャラの一部への所見も、対象範囲が分かるときだけ限定する。

通常入力のreviewには `annotations[]` を持ち、要素ごとに対象run/candidateと星・良いところ・悪いところ・任意メモを保存する。比較対象が不明ならrun参照と不明状態だけでよく、存在しないcandidateや生成条件を作らない。お気に入りだけの再評価も4.4の履歴規則を使い、対象・評価者・用途が同じ記録の新版を通常表示する。

## 5. 評価対象の識別

関係は次のとおり。画面では日本語名を出し、IDは詳細で確認できればよい。

```text
run（学習の1回の起動）
  └─ artifact（epoch30 / final / final_raw / raw / center 等）
       └─ candidate（生成に使った成果物の組と強度等）
            └─ review（特定の画像集合を見た、各軸・実用性・採用の判断）
```

### 5.1 run

- 新しい記録は既存 `run_records/<UUID>` のUUIDを使用する。
- 旧runは台帳用UUIDを発行。名前、更新日時、出力フォルダだけで同じrunへ統合しない。
- `training_status` は完了／途中終了／失敗／不明を持ち、根拠を別保存。finalの存在だけから完了へ確定しない。
- resume・追加学習は別runとし、分かる場合だけ親runと再開成果物を保存。関連するrunは分析時に同じ系統として扱う。
- `purpose` は通常学習／試験／診断／不明の粗い分類。「学習の目的」の自由文は別に `user.experiment_note` へ保存する。名前からの自動分類は候補表示に留め、人の訂正を保存する。

### 5.1.1 名前を後から直したrun

**利用者がメモで使っている、修正後の現在のファイル名を人向けの名前として優先する。メタ情報の名前と違うだけではエラーにしない。** 名前の選択、設定の取得元、同一実行の判定を分ける。

| 項目 | 内容 |
|---|---|
| `display_name` | ユーザーが修正できる台帳上の名前。初期値は選択した現在のファイル名由来。内部output nameへ巻き戻さない |
| artifactの現在の参照・ファイル名 | 実際に開くファイル。epoch等の接尾辞も元の文字列を保存 |
| `metadata_output_name` | ファイル内の `ss_output_name` をそのまま保持。学習時の名前として表示 |
| `aliases` | 登録時の名前、観測できた改名前の名前、ユーザー指定のメモ上の別名。各名前の由来を保持 |
| `rename_note` | 「output nameの変更忘れにより、学習後にrun_Bへ改名」等の任意メモ |

例：現在のファイルが `run_B.safetensors`、内部が `ss_output_name=run_A` なら、一覧はrun_B。詳細には「学習時のoutput name：run_A」と表示し、設定はrun_Bファイル自身のメタ情報から取得する。外部メモの「run_B」はその候補を先に探す。メタ情報を書き直す機能は不要。

検索は表示名・現在のファイル名の一致を優先し、旧名一致は由来付きの候補として表示する。ユーザーがメモの参照先を確定したらIDで保存する。現在名でも候補が複数なら自動決定しない。旧名run_Aを共有する別runやそのログを一括結合しない。

最終版だけ改名し、中間checkpointには旧名が残る場合も、各ファイルのsession・開始時刻と設定の整合性で対応候補を照合する。表示名を揃えるために元ファイルの一括改名を要求しない。複数ファイルのメタ情報が違えば、artifactごとの出典と差を残す。

すでに上書きされた前の学習の設定・重みは、新しいファイルのメタ情報から復元できない。前の実行は別メモや残存ファイルに基づく記録として保存し、現在のファイルの設定を前の実行へ割り当てない。改名した重みと、上書き前後が混ざり得る旧名のログとの対応も別途扱う。

内容hashを登録済みのファイルが改名された場合は、一致を確認して参照を追加・更新し、artifact IDを保持できる。hash未取得ならsession等から候補を出し、名前だけの自動付替えはしない。

### 5.2 artifact

- 台帳で一意のartifact ID、親run ID、ファイル参照、epoch・stepとその出典、成果物の種類とその根拠を持つ。
- 同epochのfinalとfinal_rawは別artifact。同じ内容の別パスは同じ内容への追加参照にできるが、異なるrunを内容一致だけで統合しない。
- `_raw`、`_center`、`_final_raw` 等の名前は種類の候補。旧ファイルの内容・由来を名前だけで確定しない。
- `live/promote` 途中のrawは、それ以前の平均化・採用の影響を受け得る。「平均化なしで学習した対照」として扱わない。
- 既存artifactと同じパスで内容が変わった場合は、旧artifactの参照をchangedにする。新しい内容は別artifactとして登録し、旧評価を移さない。
- 後処理の平均・合成・移植は、由来が分かる範囲で複数の親artifactへの参照と処理名を保存できる。未対応の加工形式は `unknown` とし、単独runの効果分析へ混ぜない。

### 5.3 candidateと生成条件

candidateは1本のLoRAに限らず、順序付き `components[]` を持つ。各要素にartifact ID、元の強度指定、解釈できる場合のTE1/TE2/UNet強度、LBW指定を保存する。複数LoRAの同時使用・合成の評価を、各runに同じ成功ラベルとして付けない。

共通の生成条件として、生成base model・VAEの参照と識別状態、sampler、steps、CFG、解像度、prompt、negative、生成seed、生成プログラムの版（分かる場合）、その他の生成設定の小さな控えを保持する。学習seedと生成seedは別キー。

既存 `metadata.json` と `config.json` を正式な取込口にする。configが指定した予定ケースと、jobが成功して実際に閲覧したケースを分ける。ケース単位で候補が欠ける場合は、利用可能な候補だけをそのケースの比較対象にする。

以前の画像が指す重みの同一性を、現在そのパスにある重みをhashしただけで証明したことにはしない。`content_verified_at_review` と `generation_link_verified` を区別する。生成当時のhashがなければ後者は未検証になり得る。

### 5.4 データセットの名前と内容

`dataset` は次を分ける。

| 項目 | 用途 |
|---|---|
| family_id・表示名 | 人が同系列として探すための安定IDと名前 |
| version_label | v1、caption修正後等。未記録も許す |
| content_fingerprint | 画像・caption等の入力内容の指紋。存在するときだけ |
| identity_status | 学習時の内容記録で確認／人が同一と申告／設定構造だけ一致／不明 |
| provenance | 確認日、確認者または取込元、何を比較したか |

同じキャラクター名・同じフォルダ名は、同一内容の証明ではない。画像、caption、繰り返し、subset、解像度などの設定差を別に持つ。画像・captionの内容同一性と、学習でどう使ったかも分ける。

過去runに現在のフォルダ内容を遡及して確定しない。初版では全画像・captionの自動hashを必須にしない。人の「同じデータセットを使った」という申告は、その根拠区分のまま比較に使える。

## 6. 保存形式

```text
lora_ledger/                       リポジトリ外。任意の保存先へ変更可能
  ledger.json                      schema、台帳ID、評価基準、参照先の探索設定
  locations.local.json              root名 → ローカル絶対パス
  runs/<run_id>.json                run、入力、ログ参照、artifact一覧
  reviews/<review_id>/0001.json     評価カード（保存ごとの版を追記）
                     /0002.json
  history/runs/<run_id>/...json     登録情報の変更前の控え
  cache/                           再生成できる走査索引。削除しても評価は消えない
  exports/                         GUI一覧のCSV等。正本へ自動書戻ししない
  derived/<export_id>/              再生成できる分析用出力
  research/<analysis_id>/           分析コード、報告、仮説と検証履歴
```

論理上の正本は台帳設定、runカード、reviewカード。`locations.local.json` は保存場所の対応表であり、分析上の同一性そのものではない。`derived` は正本を編集する入口にしない。`research` の解釈・所見は再生成できる数表と区別し、台帳・評価と一緒にバックアップする。

すべてUTF-8のJSON。`schema_version` を持ち、未対応の新版は読込状態を表示して書き換えない。日時はタイムゾーン付き。旧記録の時刻が曖昧なら元の文字列と不明状態を残す。

### 6.0 ツール・設定・台帳の置き場所

ツール本体はsd-scripts内でコードとして管理し、台帳はリポジトリ外に置く。以下は架空の配置例であり、ドライブや親フォルダ名は任意。台帳の作成先は初回起動時に選択する。

```text
D:\lora-workspace\
  sd-scripts\                         Gitで管理するツール
    lora_ledger_gui.py                 PySide6の起動入口
    lora_ledger_gui.bat                ダブルクリック用の起動ファイル
    tools\lora_ledger.py              同じ処理を呼ぶ任意のCLI
    tools\lora_ledger_core\           台帳処理・GUI部品
    docs\lora-research-ledger-spec-ja.md
    .local\lora_ledger_gui.json        Git除外：前回開いた台帳・画面状態

  lora_ledger\                        Gitリポジトリ外の台帳
    ledger.json                       参照先の探索設定・台帳の基準
    locations.local.json              参照先の実パス
    runs\  reviews\  history\  research\
    cache\  exports\  derived\

  lora_output\                        既存の元ログ・重み・診断
  lora_reports\                       必要なら追加する画像比較の参照先
```

| 設定の種類 | 保存先 | 理由 |
|---|---|---|
| 最後に開いた台帳、ウィンドウ位置、列幅、並び順 | リポジトリ内 `.local/lora_ledger_gui.json` | このGUI・PCの起動状態。消えても台帳を開き直せる |
| どのrootを探索するか、有効・無効、相対探索パス、再帰・除外設定 | 台帳内 `ledger.json` の `sources[]` | 台帳を移動・バックアップしても探索の意味が残る |
| root IDに対応するローカル絶対パス | 台帳内 `locations.local.json` | 保存ドライブの変更を1か所で反映できる |
| 評価・メモ・登録情報 | 台帳内 `runs/`、`reviews/`、`history/` | コード更新・Git操作から独立させる |

`sources[]` はroot IDと相対探索パスを参照し、絶対パスを重複保存しない。GUIの「参照先設定」が両ファイルを一括管理するため、ユーザーはJSONを直接編集しなくてよい。

実装時は `.gitignore` に `/.local/lora_ledger_gui.json` を追加する。重要な台帳設定は一時フォルダ `.tmp` へ置かない。リポジトリ内の設定が消えても「既存台帳を開く」で復帰でき、台帳側の参照先設定を再入力する必要はない。

起動ファイルはリポジトリのvenvを基準にGUIを起動し、コマンドを入力しなくても使えるようにする。台帳の新規作成・既存台帳を開く操作をGUIへ用意する。前回の台帳が見つからない場合は、その場所に空の台帳を自動作成せず、保存先を選び直せるようにする。

台帳保存先はリポジトリの外とし、参照する元ログの探索対象にも入らない場所を選ぶ。GUI起動状態以外の書込みは選択中の台帳内へ集める。保存先が読み取り専用の場合は閲覧のみ可能と明示する。

### 6.1 runカードの主な区分

| 区分 | 内容 |
|---|---|
| 識別 | schema、run ID、ID出典、表示名、実行日時、親run、目的、学習状態 |
| 入力 | dataset、学習base model、training seed、設定記録への参照 |
| 設定の控え | optimizer、rank/alpha、LR、DQ、avg、TE対象、batch等の小さな値と出典 |
| source_refs | ログ、設定、診断JSON/HTML、外部研究集計の参照 |
| artifacts | 個別重みのID、役割、座標、出典、参照 |
| user | 表示名・別名、改名メモ、分類、同一性申告、学習の目的・経緯など人の入力 |
| bookkeeping | 登録日時、取込器版、改訂番号、監査状態 |

自動取得部分と `user` 部分を分離し、再スキャンで人のメモや申告を消さない。設定は、元記録の取得元・取得状態を継承する。既存の照合規則に反してmanifestとcheckpoint metadataの欠落項目を混ぜて補完しない。

reviewカードには `review_id`、`revision`、対象範囲、背景情報、分かる生成条件、`candidates[]`、閲覧したケース集合、通常入力の `annotations[]`、軸別の判断、候補別の実用性、採用、理由、証拠への参照をまとめる。メモだけの記録では未入力の比較・生成条件を必須にしない。candidateはこのカード内に保存し、独立した管理画面や正本ファイルを増やさない。同じ比較レポート内では保存済みのcandidate IDを再利用し、強度・LBW・構成重みを変えた条件は別candidateとする。別レポートの同名条件は、自動で同一視しない。

### 6.2 ファイル参照

```json
{
  "root": "training_archive",
  "relative_path": "example/run03/rank_logs+example.txt",
  "observed": {
    "size": 12345,
    "mtime_ns": "例では省略",
    "sha256": null,
    "fingerprint_status": "stat_only"
  },
  "association": {
    "status": "user_asserted",
    "method": "manual_confirmation",
    "note": "この学習のログとして保管していた"
  }
}
```

上は構造説明用。実データのsize等は自動取得し、実装のスキーマ検証に従う。

参照には、置き場所、ファイルの内容同一性、runとの対応の確かさを別々に保存する。`exists`、`missing`、`changed`、`unreadable` と、`verified`、`user_asserted`、`candidate`、`conflict` を1つの状態へ潰さない。

場所はroot名と `/` 区切りの相対パス。ドライブ移動はroot対応表だけを変える。Windowsの大文字小文字・区切り文字を整理し、パスはrootの外へ抜けないよう検証する。別の場所を参照する場合は別rootを登録する。

### 6.3 同一性確認の費用を分ける

- 通常スキャン：サイズ・mtime・既存ID、必要なヘッダーを確認する。`stat_only` を内容一致と表示しない。
- 小さいJSON・設定・評価の証拠：取込時にSHA-256を計算して保持する。
- 選択した重み：評価保存時に原則としてその2〜3候補だけSHA-256を計算・再利用する。キャンセルや読込不能なら評価は保存でき、未検証として残る。
- 大きいログ：特徴量を初めて抽出する読込と同時にhashを取る。全重みの一括hashは別の明示操作とする。
- 通常の再スキャンはstatによる変化検出。サイズ・mtimeが同じ変更も調べる完全検証は明示操作でhashを再計算する。

読込前後でサイズ・mtimeが変わったファイルは確定しない。hash一致は読んだ内容の一致であり、学習成功・保存時刻・生成時の使用実績の証明ではない。

### 6.4 保存と訂正の安全性

1プロセスからの書込みを基本とし、保存時は台帳ロック、改訂番号の照合、一時ファイルへの書込、置換を使う。同時編集は後勝ちで上書きせず、保存競合を表示する。

run更新は変更前の控えの保存が成功してから置換する。評価は未使用の版番号へ原子的に保存する。起動時は最後の完全な版を読む。途中で壊れた1件があっても他の一覧を開ける。

誤った紐付けを直してもartifact IDや古い評価対象を黙って別のものへ付け替えない。訂正の旧値・新値・理由を残し、紐付け訂正で影響する評価・集計を再監査対象にする。

ファイルが消えても登録カードと評価を消さない。台帳は元データのバックアップではないため、元ログ・重みの保管は従来どおり必要。

## 7. 登録・取込の規則

### 7.1 対応を確定する優先順

1. 既存run IDと、読めるcheckpointのsession ID・学習開始時刻が整合する記録。
2. 既存の内容hash・記録された参照等による対応。
3. 人による対応の申告。確認根拠を残す。
4. 名前・近接フォルダ等による候補。仮登録のまま。

session・開始時刻・設定内容に矛盾があるときは優先順位だけで押し切らず `conflict`。現在のファイル名と内部output nameの不一致だけは改名候補として扱い、`conflict`にしない。同名run、resume、ログの追記・step巻き戻りを、日時順で自動分割・統合しない。旧ログの区間対応が確定できなければ、閲覧可能だが厳密な比較から除外する。

再登録は同じroot・正規化参照と既存の識別情報を照合し、同じ対象を増やさない。既存カードに追加の参照や診断を結び付ける。同じrun名の別実行を上書きしない。コピーされた診断JSONが増えてもrunを増やさない。

runとcheckpointのsession一致は、同じ名前の各ログの出自まで証明しない。参照ごとに対応状態を保存する。

### 7.1.1 設定ファイルがない旧checkpointの設定取得

メタ情報からの設定取得を初版の必須機能とする。設定ファイルがないこと自体を登録エラーにしない。

1. 選んだcheckpoint自身のsafetensorsヘッダーからメタ情報を取得する。tensorやGPUは不要。現在のファイル名と内部output nameの一致は取得条件にしない。
2. 対象runと対応が確認できる設定ファイルがあればそれを優先する。対象の設定記録がなければ、対象checkpointのメタ情報を設定の出典にする。
3. 学習率、optimizer、rank/alpha、network引数、学習seed、epoch、dataset構成、noise/caption設定等、記録されている項目を読む。元キー・元値と正規化した値を出典付きで保持する。
4. 未記録の設定は不明。文字列 `None`、0、false、空欄、不正値を区別し、現在の既定値や別runの設定を入れない。共通TE LRを未記録のTE1/TE2実効LRへ展開しない。
5. 出典のartifact ID、現在の参照、読取時刻、headerのhash等の読んだ証拠、部分設定であることを記録する。同じrunの複数checkpointでは出典を保持し、設定差があれば表示する。

出典は「このcheckpointに記録された設定」。全実効値・コード版・完走が完全に復元されたという意味にはしない。メタ情報由来の設定と、外部メモの実験目的・補足は分けて保存する。

同じoutput nameの別sessionの設定ファイルを今回の設定として採用しない。sessionから別実行と判定できれば候補から外し、今回のcheckpointメタ情報を利用する。設定記録の破損や対応不明が残る場合も、読めたcheckpointメタ情報は独立した出典として表示・保存し、未解決状態を併記する。「設定ファイルが無い」と「設定ファイルが壊れている」は区別する。

対応済み設定ファイルが不完全な場合は、その欠測をmetadataで項目単位に埋めない。設定ファイルの値とcheckpointの値を別の出典として保持し、分析でどちらを使ったかを記録する。実行との対応に疑義がある場合は、設定が読めても比較条件確認済みへ自動昇格させない。

現行 `tools/lora_training_settings.py` の `read_metadata()`、`normalize_metadata()` 等の読取・型変換を再利用する。一方、現行 `load_training_settings()` は同名manifestとの不一致・破損で戻る場合があるため、その戻り値だけで台帳のメタ情報取得を打ち切らない。台帳側で名前管理と出典選択を分離する。既存診断レポートの読込規則は変更しない。

### 7.2 初版で対応する入力

| 入力 | 初版の扱い |
|---|---|
| run_records manifestと設定JSON | 検証して識別・設定の控えを取込 |
| 診断JSON | 構造を検証し、参照・設定・利用可能な指標を取込。旧形式も欠測を保ったまま対応 |
| checkpoint | 一覧・ヘッダー、設定ファイルがない旧学習のメタ情報由来の部分設定。改名済みも対応。tensor解析は別処理 |
| 画像比較のmetadata/config | 候補・生成条件・画像ケースへの参照を取込 |
| 既存研究のfiles/epoch_metrics等 | 読み取り専用の任意入力。出典hashと定義・版が一致する集計だけ再利用 |
| gradient/DQ/rank/avg等の元ログ | 登録では参照。分析出力時に必要な列・区間だけストリーム抽出 |
| 古い文章・手書き評価 | 出典へのリンクと人が確認した判断を保存。文章からの推定勝敗を自動確定しない |
| HTMLだけの古い評価レポート | 証拠へのリンクと手動評価。任意HTMLの実行・汎用スクレイピングを取込手段にしない |

古い集計のhashと現在の元ログが異なる場合、過去版の集計としては保存できるが、現在のログの集計として採用しない。再計算か、過去版に限定した分析を選ぶ。

### 7.3 ブラインド投票

初版の完成条件は台帳画面で比較単位の評価を保存できること。過去に保存されなかったブラウザ上の票は復元しない。保存済みの研究評価はその形式を確認できる範囲で手動・専用取込を行う。

画像単位の票を日常的に残したくなった時点で、既存ブラインドHTMLへ「投票JSONを保存」を追加する小さな拡張を行う。この拡張は初版後の第2段階とする。

その交換形式は `comparison_votes`、`schema_version`、report/configのhash、評価日時、case ID、candidate ID、軸、勝者・同点・保留、提示候補、提示順、Reveal前後を保存する。同点・保留・未評価の区別を維持する。再取込はreport・case・評価IDで重複を検知する。

## 8. 画面と実装境界

### 8.0 主画面：一覧を見ながら、その場で記入

一覧・詳細・評価は1つのメインウィンドウへまとめる。別画面への往復を減らすため、左を絞込みと学習一覧、右を選択項目の詳細・入力欄にする。再走査結果と参照先設定は必要時に開くダイアログ。

```text
[台帳を開く] [参照先設定] [再走査]                       [CSV出力]
[検索..................] [dataset] [★] [未評価のみ]
+-----------------------------+--------------------------------+
| 学習一覧                    | 選択した学習名                 |
| 名前 / 対象 / ★ / 目的      | [重みを選択] [全体の印象]      |
|                             | お気に入り度 ☆☆☆☆☆            |
|                             | 学習の目的・経緯               |
|                             | 良いところ                     |
|                             | 悪いところ                     |
|                             | 任意メモ                       |
|                             | [保存]  保存状態               |
|                             | [設定とログ] [評価履歴]        |
|                             | [比較を記録] [詳しい評価]      |

```

ソート・検索・星の絞込み、キーボードでの行移動、Ctrl+S保存、レポートと保存フォルダを開くボタンを提供する。入力途中の行切替・終了時は「保存／破棄／戻る」で取りこぼしを防ぐ。通常はJSONやExcelを開かずに操作を完了できる。

「学習の目的」はrun全体の欄。選択重みを切り替えても同じ内容を表示する。他の4欄は対象重みまたは「全体の印象」の評価を表示し、対象切替で星や所見を別の重みへコピーしない。

### 8.1 一覧

標準列：データセット、学習名（修正後の現在名を基本）、対象重み・強度、お気に入り度、学習の目的の短い抜粋、メモの有無。設定差・実用性・比較判断・要確認は詳細または列の追加で表示する。本文の全文は詳細画面で読む。

絞込み：データセット、お気に入り度、未評価、実用性、通常学習／試験、ファイル不明・対応不明。検索：表示名・現在名・旧名・目的・良いところ・悪いところ・任意メモ。複数の用途・評価がある場合は「複数評価」と対象を表示し、単一のrun合否や最大の星へ圧縮しない。run全体の星と特定重みの星は対象表示で区別する。

### 8.2 詳細

設定の要約と出典、成果物一覧、評価履歴、ログと既存レポートを開くボタンを表示する。欠測・対応矛盾は該当欄の近くへ出す。詳細なDQ・rankのグラフを台帳に再実装しない。

### 8.3 評価

通常は選択中のrun・重みについて4.5の5項目を表示する。自由文は短い入力枠から必要に応じて広げられる。全欄任意で、星だけ・目的だけ・一言だけの保存ができる。「比較を記録」「詳しい評価」は折りたたみとする。

「比較を記録」を開いた場合は既定2〜3候補。多い場合は評価対象を選べる。画面上部に用途、対象重み、強度、画像集合、閲覧範囲を表示し、総合判断、実用性と2軸と各理由を任意入力できる。軸が異なる判断や「全部使える」「全部使いにくい」を自然に保存できることを優先する。

目標は、画像を見終えた後の基本入力をおおむね1分以内に終えられること。これはUIの受入れ目標であり、画像閲覧・初回hash・曖昧な旧ログの整理時間は含まない。

### 8.4 技術構成

- PySide6 / Qt WidgetsでデスクトップGUIを作る。既存 `sdxl_lora_report_gui.py` と同じ依存を利用する。PySide6は既存のrequirements.txtに含まれる。
- 台帳処理・走査・反映はGUIから独立させ、GUIとCLIで共通利用する。ブラウザサーバー・HTTP API・QtWebEngineは初版に不要。
- 走査・hash・集計はワーカーで実行し、進捗・中止を表示する。UIスレッドで大きいファイルを連続読込しない。中止しても保存済みの台帳・評価は保つ。
- 登録・評価・既存集計からの出力はGPU、torch、trainer import不要。重みの追加分析だけ独立した任意処理にする。
- 一覧はモデルから表示し、大量行に対して行ごとの重いウィジェットを作らない。詳細情報は選択時に読む。
- 画面の保存は共通の台帳処理を通し、JSONの版管理・原子的な書込み・同時編集検知を守る。
- 診断HTML・画像比較HTMLは標準ブラウザで開き、フォルダはExplorerで開く。既存レポートをGUI内に再実装しない。ファイル参照をシェルコマンド文字列へ組み立てない。

CLIのインターフェース：

```text
python tools/lora_ledger.py init --ledger <台帳フォルダ>
python tools/lora_ledger.py scan --ledger <台帳フォルダ> --source <出力フォルダ>
python tools/lora_ledger.py register --ledger <台帳フォルダ> --source <出力フォルダ>
python lora_ledger_gui.py --ledger <台帳フォルダ>
python tools/lora_ledger.py verify --ledger <台帳フォルダ> [--full]
python tools/lora_ledger.py export --ledger <台帳フォルダ> --selection <選択条件JSON>
```

`scan` は正本へ登録せず候補を表示する処理（再生成できる走査キャッシュのみ更新可）、`register` は差分反映、`verify` は参照監査、`export` は分析材料の生成。`--source` を省略した場合は台帳に保存した有効な参照先を使う。GUIの通常操作でも同じ処理を呼ぶ。初版で学習終了フックやユーザーのbatを一括変更しない。

### 8.5 GUIとExcelの使い分け

普段の閲覧・編集はGUI、Excelは書き出した表の並べ替え・集計・共有に使う。正本はJSONの台帳1つとし、CSV編集を自動で戻す同期機能は初版に入れない。名前・重み・比較・履歴の関係を平坦なCSVだけで管理すると失われるため、書出しと編集を分ける。

「CSV出力」には「現在の一覧」「評価の詳細」「AI分析用一式」の3つを用意する。現在の一覧は画面の絞込み・列・並び順を反映し、データセット、表示名、現在名、対象重み、★、目的、良いところ、悪いところ、任意メモ、設定の主要項目、出典状態等から列を選べる。

評価の詳細は1評価対象・1review版を1行にし、run/artifact/review IDと対象範囲を必ず含める。同じrunに複数の評価がある場合、勝手に最大の星や直近の違う対象の所見へまとめない。既定は有効な最新版だけ。履歴を含める選択は別にする。

出力先の初期値は台帳内 `exports`。保存先を選べ、出力後にファイルかフォルダを開ける。CSVは日本語と改行・引用符を保持する形式で保存し、Excel向け出力ではUTF-8 BOM、CRLF、適切な引用符処理を行う。日時とIDの列定義を添える。Excelが数式として解釈する先頭文字を持つ自由文はExcel用出力で文字列化し、変換したことを明示する。元のJSONとAI分析用の原文は変更しない。

CSVは出力日時点のスナップショット。Excelで変更しても台帳には反映されないと出力画面へ表示する。Excelで開いていて上書きできない場合は別名保存を案内し、台帳の保存処理へ影響させない。

## 9. 分析用出力

### 9.1 出力するファイル

| ファイル | 役割 |
|---|---|
| README.md | 対象、使える比較、欠測、解釈上の制約、元データの開き方 |
| runs.csv | 1run1行の識別・部分設定・対応状態 |
| candidates.csv | 評価に使った成果物と生成条件 |
| reviews.jsonl | 有効版の人間評価。未評価・同点・保留と理由を保つ |
| comparisons.csv | 軸・case集合・判断イベントごとの候補対と結果 |
| features.csv | 対象・区間・指標定義ごとの数値。必要な10〜20指標から開始 |
| feature_definitions.json | 指標、分母、集約順序、座標、欠測、利用時点の定義 |
| issues.csv | 対応不明・欠測・変更済み・除外理由 |
| export_manifest.json | 台帳ID、選択条件、run/reviewの版とhash、元参照のfingerprint、抽出コード版、生成日時 |

`features.csv` は `subject_id, metric_id, scope, target, window_id, value, status, n_valid, n_missing, source_ref, definition_version` 等の縦持ちを正規の出力とする。分析時の横持ち表はここから生成する。設定値・評価ラベル・派生特徴量を同じ意味の数値として混ぜない。

同点、保留、未評価はそのまま出力する。勝率を出す場合は勝ち・負け・同点・保留の件数と分母を併記し、同点を勝手に勝ち0.5へ変換しない。分析方法として0.5を使う場合は方法を明記する。

### 9.2 抽出元の選び方

1. 定義・対象区間・source hashが目的に合う既存研究集計があれば再利用。
2. 診断JSONで定義と対象が確認できる項目は利用。
3. 必要な列・Scope/Target・区間が不足する場合だけ元ログから抽出。
4. 情報が足りなければ欠測と理由を出力。現行既定値、別run、未来の観測で穴埋めしない。

既存研究集計に依存しなくても初版は使えること。ファイル配置が違う環境ではその接続を省き、元ログの必要部分を解析する。

### 9.3 初期特徴量

全指標を全runに強制しない。DQ、rank、avgの実データを持つ比較だけ対応する特徴量を作る。

| 系統 | 最初に用意する指標例 | 主な出典・制約 |
|---|---|---|
| loss | 終盤中央値、直前区間からの変化 | 生loss。MAと区別。diffusionの学習条件が違うrun間の絶対値比較を品質判定にしない |
| DQ | QuantErrRatioEMAの終盤中央値と変化、QuantErrRMSEMAの中央値、入力RMSの中央値、ClipRateEMAの中央値、RangeMulの変化 | Scope/Target、metric版、Bits、mode等を保持。比率増加が小さい入力RMS由来かを確認 |
| DQ auto | 記録されたauto判断件数、適用件数、escapeの有無 | 分母は記録された判定機会。全更新回数や全学習step数ではない |
| rank | RankSatP95、RankTop1P95、RankEnergySumの終盤値・変化 | 現行rankログのScopeはUNet。module集合とrank/alphaを確認 |
| avg | 保存候補に対応したproxy lossの相対差、実採用回数、候補mode | rawとcandidateの同じbank・epochでの比較。center未保存なら画像評価と直結しない |
| 補助 | LRの範囲、group loss、勾配のScale併記 | 基本設定・補助情報。指標の意味が確認できた比較だけ追加 |

RankSatは既存の実効rank由来の指標を使う。新たな重み分析ではその計算をまず再利用できるか確認し、同じ意味の指標を重複実装しない。

### 9.4 区間・集計方法を固定する

- 基本座標は、出典が確認できるepochを使う。元のepoch/stepと0始まり・1始まりの変換規則を残す。
- checkpointまでの観測を対象にする。checkpointのepochが不明ならcheckpoint用の時系列特徴量は作らない。
- 区間の選び方を2つに分ける。同時期のrun間比較は `common_interval` として共通範囲、同一runのepoch30対final等は `checkpoint_local` として各成果物までの範囲を使う。後者は学習時期・長さが違う比較であることを表示する。両方を同じwindow IDにしない。
- 選んだ範囲のepochを昇順に取り、n個のepochの正規化位置を `i/(n-1)` とする。n<5なら終盤変化は不足扱い。
- 初期の直前区間は位置0.6以上0.8未満、終盤は0.8以上1.0以下。両区間が空でない場合だけ差を出す。利用したepoch一覧・実step範囲を出力する。
- これは観測範囲内の位置。予定の学習完了率ではない。8epoch試験と40epoch学習の終盤を同一条件として集計しない。
- 1epoch内で同一定義の時点値を要約してから、epochを等重みで期間集約する。各平均・中央値・分位点は `feature_definitions` で一意に指定する。
- per-module rankは、まず同じ時点のmodule集合を扱う。moduleの行数が多いrunに重みを付けず、集合の変化・共通部分・欠落を区別する。
- 数値差は原則「終盤代表値−直前区間代表値」。相対差を作る場合は分母を明示し、0分母は欠測とする。分位点は `(n-1)q` の線形補間。
- 不規則な観測の件数割合を、時間割合と呼ばない。観測がない区間を補間して新しい観測数にしない。
- legacy研究の既存集約（等重み平均等）と上の新規特徴量が違えば別metric IDにする。名前の近さだけで互換にしない。
- 正確なstep対応がある場合だけstepでjoinする。診断JSONの推定global stepをavgイベント等の厳密照合に使わない。

平均版とraw版が同じepochなら、その時点までの通常の学習ログは共通の背景情報になる。候補の差を説明するには、候補別proxy score・重み解析等を用いる。同じ学習ログを2本の独立した学習として扱わない。

`null`、未記録、0、false、明示的な未指定を区別する。非有限値は件数と状態を残す。行の巻き戻り、同座標の矛盾、区間不足もissuesへ出す。

## 10. 研究の勝ち筋と判定方法

### 10.1 現時点の判断

**小さく作る価値はある。既存ログに成果物ごとの人間評価を結び付けることで、検証可能な仮説を蓄積できるからである。**

例えば、avg採用前後のlossの変化、rankの全体代表値と局所変化の違い、量子化指標の全期間相関と層別相関の違いは分析候補になる。ただし、ログに違いが見つかることだけでは、好まれる画質を予測できるとは言えない。人間評価との対応を別途検証する。

初期費用を回収する順序は、(1)探せる・理由を思い出せる、(2)次に見る候補を絞れる、(3)新しい学習にも通用する経験則を検証する、の順とする。

### 10.2 優先する仮説

| 優先 | 問い | どのような結果なら役立つか | それだけでは言えないこと |
|---|---|---|---|
| 1 | 同一runの平均版とraw版で、内部scoreと好みは一致するか | 保存済みの対で、proxy改善が自然さ・本人らしさのどちらと対応するかが繰り返されれば、確認すべき版を絞れる | proxy scoreが普遍的な画質スコアだという主張。学習中avgの因果効果 |
| 2 | 途中checkpointと最終版の好みが逆転するか | loss改善中でも途中版が選ばれる比較が反復すれば、最終版だけを見る運用を変える価値 | ログだけで最適epochを自動決定できる、早期停止して同じ結果になるという主張 |
| 3 | DQ負担の推移は自然さ・本人らしさの差と関係するか | 同じdatasetと近い条件内で、相対誤差・絶対誤差・入力RMSを併せた傾向が特定の評価軸と対応すれば、要確認runを絞れる | QuantErrRatioが高ければ必ず悪い、auto調整が原因で悪化したという主張 |
| 4 | rankの局所変化・TE/UNetの分布と評価軸の違いは結び付くか | 特定の層分布の違いが同条件内の選好差で再現すれば、次の設定・強度調整を選べる | 大きなnormやrankが常によい、単一の総量で本人らしさが決まるという主張 |

優先1・2は同じrunの対応済み成果物があれば、datasetや学習seedの差を減らして比較を始めやすい。final/final_rawや途中checkpointを候補とし、同epoch・同sessionなどの条件が揃うか、現在のファイルと由来を確認する。

どのテーマも、実際に評価が残っていて対応が確かな比較を優先する。適切なraw/平均版の対がなければ、無理に優先1を埋めず、既存のrun間比較から始める。

### 10.3 誤った結論を作らない分析単位

1. 同じdataset内容または同一性申告のまとまり、近いbase model・設定、共通の生成条件内で候補対の差を見る。複数設定が違う場合は全差分を示し、特定設定の効果と断言しない。条件を揃えて比較する考え方は [NISTのブロック化の説明](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm) を参照。ただし過去の試行錯誤を無作為化実験とは扱わない。
2. ログ行数、checkpoint数、画像数、training seed数、独立run数、dataset系列数を別々に数える。画像票が多いrunが全体を支配しないよう、まず比較単位へ要約する。
3. 採用済みだけでなく、評価できる不採用候補も残す。候補数や選抜方法が違う比較の「第一候補率」をそのまま比較しない。
4. 同点・判断保留・未評価を保つ。記憶評価、選別画像、生成条件不明、run対応不明は別の集計区分にする。
5. 過去の探索は相関・反例探しとして扱う。多数の指標から好都合なものを選んだ結果を検証済みと呼ばない。
6. 予測を検証する場合は、同じrunとresume系統を分離しない。未知datasetへの一般化を言うならdataset系列ごとにholdoutする。グループを分ける検証の考え方は [scikit-learn公式資料](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data) を参照。
7. 早いcheckpointを選ぶ研究では、その時点より後のログ・重み・最終評価由来の特徴量を入力にしない。観測終盤の特徴は事後分析用と明記する。
8. 勾配の閾値超過をskip率にしない。既存group lossはskipや非有限値等を含む全提示台帳ではない。生Normの大きさだけで異なるscaleのrunを順位付けしない。

研究用の比較区分は `controlled`（今回の問い以外の確認済み条件が揃う）、`observational`（人の申告を含む実用上の比較）、`unresolved`（対象や条件が未確定）を都度導出する。区分と理由をexportへ保存する。未確定でも一覧や記憶の記録として使い続けられる。

### 10.4 重みの追加解析

気になる比較だけをCPUで逐次解析し、結果は `derived` または `research` に保存する。登録や評価保存の必須処理にしない。

通常の行列型LoRAでは `ΔW=(α/r)BA` を基本に、生成強度やLBWも含めた実効更新のnorm、特異値・有効rank、層間分布、対応層間の方向差を候補にする。LoRAの分解の基礎は [原論文](https://arxiv.org/abs/2106.09685) を参照。Aをc倍、Bを1/c倍しても積は同じなので、A/B個別のRMSだけを品質の説明に使わない。

conv、LoRA以外のnetwork形式、合成・移植、学習時のDQには実装固有の解釈がある。対応する形式でだけ計算し、重みから当時の入力依存DQ挙動を完全復元したとはしない。normが似ていても画像が似る保証はない。高次元テンソルをそのまま少数評価に回帰させる処理は初版外。

### 10.5 小さく始め、続ける基準

初回は5〜10比較。統計的な必要件数ではなく、操作と対応付けの試験規模とする。

試運転の合格は、正しい重みを開ける、評価が約1分で記録できる、以前の判断が読み返せる、使える比較と不足情報が自動で出ること。これが満たされれば、法則が見つからなくても運用価値がある。

仮説を探索した後は、次に日常的に発生する比較群で方向・例外・簡単な基準（lossだけ、最終版だけ等）との差を確認する。独立した学習やdatasetが少なければ、件数を水増しせず記述的な報告に留める。特定の必要サンプル数や勝率を根拠なく完成条件にしない。

入力負担が大きい場合は任意軸を減らす。対応不明ばかりなら過去の復元を深追いせず、新しい学習の一意出力と比較条件の記録を優先する。再現しない仮説なら、台帳は続けつつ予測機能の開発を止める。

## 11. AIに相談する時の手順

1. 台帳の監査：欠測、参照変更、同名run、重複、評価対象の対応を確認。
2. 比較可能な群を作る：dataset、base model、学習条件、生成条件、評価の由来を整理。
3. 数表と図を計算する：元ログ全文を文章へ詰め込まず、コードで必要な特徴量を抽出。
4. 仮説を少数に絞る：支持例だけでなく反例・関係が見えなかった結果も報告。
5. 次の確認を提案する：既存checkpointで試せることから優先し、新規学習が必要なら理由を示す。

分析成果には「対象ID・版」「問い」「除外と理由」「方法・コード」「結果」「反例」「限界」「次の検証」「探索中／次群で確認／支持されず」を残す。人間評価をAIの推定で書き換えない。分析書込み先は `research/<analysis_id>` と派生集計のみとする。

台帳が持つローカル参照は、別環境へ送っても参照先まで移動しない。相談用exportには共有可能な小さな数表と定義を入れ、必要な元資料はその環境でアクセスできる範囲に限定する。外部送信や重みのアップロードを台帳の自動機能にはしない。

## 12. 実装順と受入れ条件

### 第1段階：初版の完成範囲

順序は、(1)外部台帳・参照先設定・差分走査と登録、(2)PySide6の一覧＋詳細・入力と履歴、(3)CSV出力・10〜20指標と既存研究への任意接続、(4)5〜10比較で試運転。

| ケース | 必須の結果 |
|---|---|
| 同じフォルダを2回登録 | run・artifact・評価が増殖しない |
| lora_outputだけを参照先に指定 | run_records・diagnostic_report・dq_dataset_profilerを役割別に検出する |
| 親と子の参照先が重複 | 同じファイルの候補が二重に出ない |
| 再走査で新runと既存runの新レポートを発見 | 新規学習と追加資料を区別し、一括反映できる |
| 同じ診断JSONの内容が変化 | 変更として出典の新版を提示し、旧出典を保持する |
| dataset診断内にsnapshotがある | 通常学習の件数へ加算しない |
| 参照先全体がオフライン | 接続不能と表示し、全件削除や評価消去をしない |
| 走査後・反映前にファイルが変更 | 当該対象を再確認へ戻し、古い読取内容で確定しない |
| 走査・集計中 | GUI操作と中止が可能。保存済み評価が失われない |
| リポジトリ内のGUI起動設定を削除 | 外部台帳を選び直せば評価と参照先設定が復帰する |
| リポジトリを更新 | 外部台帳の設定・評価を変更しない |
| 未保存の所見がある状態で行切替 | 保存・破棄・戻るを選べる |
| CSV出力後にExcelで編集 | 正本は変わらず、別の編集経路にしない |
| CSVをExcelで開いたまま再出力 | 別名保存でき、台帳の保存は失敗させない |
| 同名で再実行 | 別runとして扱い、ログ対応が不明なら仮登録 |
| 設定ファイルがない旧checkpoint | メタ情報から記録済み設定を取得し、不足項目は不明とする |
| run_Bへ改名、内部output nameはrun_A | run_Bを基本表示。run_Aを保持し、run_B自身の設定を読む。名前の違いだけで拒否しない |
| 改名済みrunと同名メタ情報の別run | 旧名一致だけで設定・ログ・メモを結合しない |
| 旧名に対応する別sessionのmanifestがある | 別実行の設定を採用せず、対象checkpointのメタ情報を取得できる |
| 最終版のみ改名、中間checkpointは旧名 | session等を用いた対応候補と出典を保持できる |
| 学習を上書きした後で改名 | 新ファイルの設定を取得し、上書き前の学習へ割り当てない |
| manifestのsessionとcheckpointが矛盾 | 矛盾を表示し、自動結合しない |
| resolved設定しかない | 完走と表示しない |
| A・B・CからBを選ぶ | B>A、B>Cだけ。AとCは不明 |
| Cは未閲覧・生成失敗 | B>Cを生成しない |
| 不採用Aが「使える」 | 値が矛盾扱いされず、そのまま保存される |
| 全入力欄が空、または目的だけ | 登録・更新でき、空の評価イベントを増やさない |
| 星だけ・良いところだけを保存 | 比較や実用性の入力を強制しない |
| 星なし／★1／同じ星の2候補 | nullと1を区別し、同じ星を対比較の同点へ変換しない |
| 学習名にだけ★を付ける | run全体の印象として保持し、全checkpointへ複製しない |
| 「機能は正式採用しなかった」と記録 | LoRAの低評価・不採用へ変換しない |
| 自由文に「Bよりよい」 | 原文を残し、相手IDや確定票を勝手に作らない |
| 同点／保留／未評価 | JSONとexportで区別される |
| 用途・軸で判断が違う | 軸ごとの値・理由が失われない |
| epoch30だけ評価 | finalや他epochに評価を複製しない |
| 複数LoRAの条件 | 構成全体に評価が付き、各runの成功数へ加算しない |
| 旧評価を訂正・再評価 | 旧版を残し、通常集計で重複票にならない |
| 同じパスの重みを置換 | 検出後は旧評価を新しい重みへ付け替えない |
| rootフォルダを移動 | root対応表の変更で参照を回復できる |
| 元ファイル欠落・変更 | 評価を保持し、使用不可の特徴量と理由を出す |
| derivedを再生成 | 人間の評価とメモが一切変わらない |
| Scope/Targetや版が違うDQ | 同じ指標として混合しない。不明なら制限を出す |
| resume、step巻き戻り | 自動的な独立run数の増加や推定stepでのjoinをしない |
| 早期checkpointの特徴量 | 後のepoch・最終重みを参照しない |
| 保存中断・同時編集 | 旧完全版を保ち、後勝ちで判断を消さない |
| 多数の重みがある初回スキャン | tensor全読込・全件SHA-256を開始条件にしない |
| 元ログ・学習コードのhash監査 | 台帳操作前後で内容が変化しない |

## 14. 初版実装の具体化

初期の標準特徴量は20種類に固定した。定義の異なる既存研究集計はlegacy.*として任意出力する。診断JSONのfallbackは勾配配列に限定し、Scope等を失ったDQや推定stepによる厳密joinは行わない。詳細は実装済みの使い方とfeature_definitions.jsonを参照する。

68件の台帳・GUIテストと27件の既存設定記録テストを確認。初回登録の評価は空欄から開始する。5〜10比較の人間評価・仮説の検証は、利用を始めた後の試運転で行う。

### データセット名・日時順の追加

記録されたdataset_configのTOML名を表示に優先し、不明ならフォルダ名または「名称不明（サブセット数）」とする。手動表示名は独立して保持し、再走査で変更しない。GUIで自動取得へ戻せる。

学習開始の記録を優先した日時列と昇順・降順ソートを設ける。不明ならcheckpointの更新日時を代用し、出典を区別する。日時不明は常に末尾。CSV・AI出力にも日時と出典を保持する。
